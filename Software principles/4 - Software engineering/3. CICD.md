# CI/CD

CI/CD stands for Continuous Integration and Continuous Delivery (or Deployment). It is a set of practices that automate the process of integrating code changes, running tests, and delivering software to production.

<a href="https://docs.github.com/en/actions" target="_blank">GitHub Actions Documentation</a>

## Continuous Integration (CI)

The practice of merging code changes into the main branch frequently (multiple times per day), with automated tests running on every merge.

**Goals:**
- Detect integration problems early.
- Prevent "integration hell" — the pain of merging branches that diverged too far.
- Ensure the main branch is always in a working state.

**A CI pipeline typically:**
1. Installs dependencies.
2. Runs the linter.
3. Runs unit and integration tests.
4. Builds the project.

## Continuous Delivery (CD)

Extends CI by automatically preparing the application for release after every successful build. The deployment to production is triggered manually.

## Continuous Deployment

Takes it further — every successful build is automatically deployed to production with no manual step.

## GitHub Actions

GitHub Actions is a CI/CD platform built into GitHub. Pipelines are defined in YAML files stored in `.github/workflows/`.

**Key concepts:**

- **Workflow** — a YAML file that defines an automated process.
- **Trigger (`on`)** — the event that starts the workflow (push, pull request, schedule).
- **Job** — a group of steps that run on the same machine.
- **Step** — a single command or action within a job.
- **Action** — a reusable unit of work from the GitHub Marketplace.
- **Runner** — the virtual machine where the job executes (e.g., `ubuntu-latest`).

*Example — CI pipeline for a Node.js project:*

```yaml
# .github/workflows/ci.yml

name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: "npm"

      - name: Install dependencies
        run: npm ci

      - name: Run linter
        run: npm run lint

      - name: Run tests
        run: npm test

      - name: Build
        run: npm run build
```

*Example — CD pipeline deploying to a server after CI passes:*

```yaml
# .github/workflows/deploy.yml

name: Deploy

on:
  workflow_run:
    workflows: [CI]
    types: [completed]
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    if: ${{ github.event.workflow_run.conclusion == 'success' }} # only runs if CI passes

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Deploy to server
        env:
          SSH_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
        run: |
          echo "$SSH_KEY" > key.pem
          chmod 600 key.pem
          ssh -i key.pem user@server.com "cd /app && git pull && npm ci && pm2 restart app"
```

## Environment Variables and Secrets

Secrets (API keys, passwords, tokens) should never be hardcoded. Store them as GitHub Secrets and access via `${{ secrets.SECRET_NAME }}`.

```yaml
- name: Run tests
  env:
    DATABASE_URL: ${{ secrets.DATABASE_URL }}
    JWT_SECRET: ${{ secrets.JWT_SECRET }}
  run: npm test
```

## Deploy Strategies

| Strategy | Description | Downtime |
|---|---|---|
| **Recreate** | Stop old version, start new version | Yes |
| **Rolling** | Replace instances one by one | No |
| **Blue/Green** | Run two identical environments, switch traffic | No |
| **Canary** | Route a small % of traffic to new version first | No |
