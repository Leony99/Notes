# Other Design Principles

Beyond SOLID, several other principles guide good software design. They are simpler and more broadly applicable — not limited to OOP.

## DRY – Don't Repeat Yourself

> Every piece of knowledge must have a single, unambiguous, authoritative representation within a system.
> — Andy Hunt & Dave Thomas, *The Pragmatic Programmer*

Duplicated logic creates maintenance burden. When the logic needs to change, every copy must be found and updated — and one will always be missed.

*Example:*

```typescript
// bad — validation logic duplicated in two places
function registerUser(email: string, password: string) {
  if (!email.includes("@")) throw new Error("Invalid email");
  if (password.length < 8) throw new Error("Password too short");
  // ...
}

function updateEmail(userId: number, email: string) {
  if (!email.includes("@")) throw new Error("Invalid email"); // duplicated
  // ...
}

// good — single source of truth
function validateEmail(email: string): void {
  if (!email.includes("@")) throw new Error("Invalid email");
}

function registerUser(email: string, password: string) {
  validateEmail(email);
  if (password.length < 8) throw new Error("Password too short");
}

function updateEmail(userId: number, email: string) {
  validateEmail(email);
}
```

OBS: DRY applies to logic and knowledge, not literally to every repeated line. Two functions that look similar but represent different business concepts should stay separate — merging them creates the wrong abstraction.

## KISS – Keep It Simple, Stupid

> Simplicity should be a key goal in design, and unnecessary complexity should be avoided.

The simplest solution that solves the problem is almost always the best one. Complex code is harder to read, test, debug, and maintain.

*Example:*

```typescript
// bad — over-engineered for a simple check
function isEven(n: number): boolean {
  return n % 2 === 0
    ? true
    : n % 2 === 1
    ? false
    : Math.abs(n) % 2 === 0;
}

// good
function isEven(n: number): boolean {
  return n % 2 === 0;
}
```

```typescript
// bad — premature abstraction
class UserValidatorFactoryBuilder {
  build(): UserValidatorFactory {
    return new UserValidatorFactory();
  }
}

// good — just write the function you need
function validateUser(user: User): void {
  if (!user.name) throw new Error("Name is required");
  if (!user.email.includes("@")) throw new Error("Invalid email");
}
```

## YAGNI – You Aren't Gonna Need It

> Always implement things when you actually need them, never when you just foresee that you might need them.
> — Ron Jeffries

Do not add functionality until it is needed. Speculative features add complexity, increase maintenance burden, and are often never used.

*Example:*

```typescript
// bad — building a plugin system before anyone asked for it
class NotificationService {
  private plugins: Plugin[] = [];

  registerPlugin(plugin: Plugin) { this.plugins.push(plugin); }
  executePlugins() { this.plugins.forEach(p => p.run()); }

  send(message: string) {
    this.executePlugins(); // nobody needs this yet
    console.log(`Sending: ${message}`);
  }
}

// good — implement what is needed now
class NotificationService {
  send(message: string) {
    console.log(`Sending: ${message}`);
  }
}
```

## Separation of Concerns (SoC)

Different parts of the code should handle different concerns and not overlap. Each module, class, or function should be responsible for a distinct aspect of the system.

*Example:*

```typescript
// bad — one function fetches, transforms, and renders
async function displayUsers(): Promise<void> {
  const res = await fetch("/api/users");
  const users = await res.json();
  const active = users.filter((u: User) => u.isActive);
  document.getElementById("list")!.innerHTML =
    active.map((u: User) => `<li>${u.name}</li>`).join("");
}

// good — each function has one concern
async function fetchUsers(): Promise<User[]> {
  const res = await fetch("/api/users");
  return res.json();
}

function filterActive(users: User[]): User[] {
  return users.filter(u => u.isActive);
}

function renderUsers(users: User[]): void {
  document.getElementById("list")!.innerHTML =
    users.map(u => `<li>${u.name}</li>`).join("");
}

async function displayUsers(): Promise<void> {
  const users = await fetchUsers();
  const active = filterActive(users);
  renderUsers(active);
}
```

## Law of Demeter (Principle of Least Knowledge)

> An object should only talk to its immediate friends.

A method should only call methods on: itself, its parameters, objects it creates, and its direct fields. Avoid chaining through multiple objects — it creates tight coupling.

*Example:*

```typescript
// bad — Order reaches deep into User's internals
class Order {
  getCustomerCity(user: User): string {
    return user.getAddress().getCity().getName(); // knows too much
  }
}

// good — ask for what you need directly
class Order {
  getCustomerCity(user: User): string {
    return user.getCityName(); // User exposes what Order needs
  }
}
```
