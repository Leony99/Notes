# Software Architecture

Software architecture defines the high-level structure of a system — how it is divided into major components, how those components communicate, and the principles that guide design decisions. It is the blueprint before the code.

Architecture decisions are hard to reverse and affect the entire system's scalability, maintainability, and performance.

## Monolithic Architecture

The entire application is a single deployable unit. All features (user management, billing, notifications, etc.) live in one codebase and are deployed together.

**Pros:**
- Simple to develop and deploy in the beginning.
- Easy to test end-to-end.
- No network latency between components.

**Cons:**
- As it grows, it becomes harder to understand and modify.
- One bug can bring down the entire application.
- Scaling requires scaling the whole app, not just the bottleneck.

```
┌─────────────────────────────────┐
│           Monolith              │
│  ┌────────┐  ┌───────────────┐  │
│  │  Auth  │  │    Orders     │  │
│  └────────┘  └───────────────┘  │
│  ┌────────┐  ┌───────────────┐  │
│  │ Users  │  │  Notifications│  │
│  └────────┘  └───────────────┘  │
└─────────────────────────────────┘
              │
         ┌────▼────┐
         │   DB    │
         └─────────┘
```

## Microservices Architecture

The application is split into small, independent services. Each service owns a single business capability, its own database, and communicates with others via APIs or message queues.

**Pros:**
- Services can be deployed, scaled, and developed independently.
- Failure in one service does not bring down the whole system.
- Teams can work autonomously on different services.

**Cons:**
- Network latency between services.
- Distributed system complexity (service discovery, distributed tracing).
- More infrastructure to manage.

```
┌──────────┐    ┌──────────┐    ┌──────────────┐
│   Auth   │    │  Orders  │    │Notifications │
│ Service  │    │ Service  │    │   Service    │
└────┬─────┘    └────┬─────┘    └──────┬───────┘
     │               │                 │
  ┌──▼──┐         ┌──▼──┐          ┌──▼──┐
  │ DB  │         │ DB  │          │Queue│
  └─────┘         └─────┘          └─────┘
```

## Event-Driven Architecture

Components communicate by emitting and reacting to events rather than calling each other directly. A message broker (Kafka, RabbitMQ, AWS SQS) routes events between producers and consumers.

**Pros:**
- Very loose coupling — producers don't know about consumers.
- Easy to add new consumers without changing producers.
- Handles asynchronous workflows naturally.

**Cons:**
- Harder to trace and debug (events are fire-and-forget).
- Eventual consistency — consumers may lag behind producers.

*Example flow — order placed:*

```
OrderService ──publishes──▶ "order.created" event
                                    │
          ┌─────────────────────────┼──────────────────────┐
          ▼                         ▼                      ▼
InventoryService           NotificationService       InvoiceService
(reserves stock)           (sends email)             (generates PDF)
```

## Layered Architecture (N-Tier)

Organizes code into horizontal layers, each with a specific responsibility. Common in Spring Boot, NestJS, and Express applications.

**Classic 3-layer:**

```
┌───────────────────────────┐
│     Controller Layer      │  ← handles HTTP requests/responses
├───────────────────────────┤
│      Service Layer        │  ← business logic
├───────────────────────────┤
│    Repository Layer       │  ← database access
└───────────────────────────┘
```

*Example:*

```typescript
// Controller — handles HTTP
class UserController {
  constructor(private userService: UserService) {}

  async getUser(req: Request, res: Response) {
    const user = await this.userService.findById(req.params.id);
    res.json(user);
  }
}

// Service — business logic
class UserService {
  constructor(private userRepo: UserRepository) {}

  async findById(id: string): Promise<User> {
    const user = await this.userRepo.findById(id);
    if (!user) throw new Error("User not found");
    return user;
  }
}

// Repository — data access
class UserRepository {
  async findById(id: string): Promise<User | null> {
    return UserModel.findById(id);
  }
}
```

## Clean Architecture

Introduced by Robert C. Martin. Organizes code into concentric layers where the **domain** (business rules) is at the center and has zero dependencies on external frameworks, databases, or UI.

```
┌─────────────────────────────────────────┐
│               Frameworks                │ ← Express, React, MongoDB
│   ┌─────────────────────────────────┐   │
│   │         Interface Adapters      │   │ ← Controllers, Repositories
│   │   ┌─────────────────────────┐   │   │
│   │   │    Application Logic    │   │   │ ← Use Cases
│   │   │  ┌───────────────────┐  │   │   │
│   │   │  │   Domain / Core   │  │   │   │ ← Entities, Business Rules
│   │   │  └───────────────────┘  │   │   │
│   │   └─────────────────────────┘   │   │
│   └─────────────────────────────────┘   │
└─────────────────────────────────────────┘
```

**Dependency rule:** source code dependencies must point inward only. The domain knows nothing about the database or HTTP.

## Serverless Architecture

Functions run on cloud infrastructure managed entirely by the provider. You deploy functions, not servers. The cloud handles scaling, patching, and availability.

**Common providers:**
- AWS Lambda
- Google Cloud Functions
- Vercel Functions (Next.js)

**Pros:** no server management, scales automatically, pay per execution.
**Cons:** cold starts, hard to run long processes, vendor lock-in.

*Example (AWS Lambda handler):*

```typescript
import { APIGatewayEvent, APIGatewayProxyResult } from "aws-lambda";

export async function handler(event: APIGatewayEvent): Promise<APIGatewayProxyResult> {
  const { id } = event.pathParameters ?? {};
  const user = await getUserById(id!);

  return {
    statusCode: 200,
    body: JSON.stringify(user),
  };
}
```

## Choosing an Architecture

| | Monolith | Microservices | Serverless |
|---|---|---|---|
| **Team size** | Small | Large, multiple teams | Any |
| **Complexity** | Low | High | Medium |
| **Scalability** | Limited | Per service | Automatic |
| **Best for** | Startups, MVPs | Large products | Event-driven tasks |

OBS: Start with a monolith. Extract services when you feel the pain of scale, not before. (See YAGNI.)
