# Documentation

Documentation is any written artifact that helps developers understand, use, or maintain a codebase. Good documentation reduces onboarding time, prevents misuse of APIs, and preserves the reasoning behind decisions.

## Types of Documentation

**README** — the entry point for any project. Should answer:
- What does this project do?
- How do I run it locally?
- How do I run the tests?
- How do I deploy it?

**Inline comments** — explain *why* a piece of code does something non-obvious. Not *what* it does (the code shows that).

**JSDoc / TSDoc** — structured comments that describe functions, parameters, and return types. Used to generate documentation automatically and power IDE tooltips.

**Architecture Decision Records (ADR)** — short documents that record *why* a significant technical decision was made. Invaluable for future team members.

## README Structure

A well-structured README:

```markdown
# Project Name

Short description of what this project does.

## Prerequisites
- Node.js 20+
- MongoDB running locally

## Installation
npm install

## Running locally
npm run dev

## Running tests
npm test

## Environment variables
| Variable       | Description              |
|----------------|--------------------------|
| DATABASE_URL   | MongoDB connection string |
| JWT_SECRET     | Secret for JWT signing    |

## Architecture
Brief overview or link to architecture docs.
```

JSDoc comments use `/** */` syntax and are placed directly above the function or class they describe.

Common tags:

- `@param` — describes a function parameter.
- `@returns` — describes the return value.
- `@throws` — describes an exception that may be thrown.
- `@example` — provides a usage example.
- `@deprecated` — marks something as no longer recommended.

*Example:*

```typescript
/**
 * Calculates the total price of an order after applying a discount.
 *
 * @param items - The list of items in the order.
 * @param discountRate - A decimal discount rate between 0 and 1 (e.g., 0.1 for 10%).
 * @returns The final price after discount.
 * @throws {Error} If discountRate is outside the valid range.
 *
 * @example
 * calculateTotal([{ price: 50, quantity: 2 }], 0.1); // returns 90
 */
function calculateTotal(items: OrderItem[], discountRate: number): number {
  if (discountRate < 0 || discountRate > 1) {
    throw new Error("discountRate must be between 0 and 1");
  }
  const subtotal = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
  return subtotal * (1 - discountRate);
}
```

## Architecture Decision Records (ADR)

An ADR captures the context and reasoning behind an important technical decision.

```markdown
# ADR-001: Use MongoDB instead of PostgreSQL

## Status
Accepted

## Context
The data model is highly variable between clients and evolves frequently.
A fixed schema would require constant migrations.

## Decision
Use MongoDB as the primary database.

## Consequences
- Flexible schema allows faster iteration.
- Loses strong relational guarantees (foreign keys, joins).
- Team must be careful to validate data at the application layer.
```

## What Not to Document

- Obvious code. `// increments counter` above `counter++` adds noise.
- Implementation details that change often — they go stale and become misleading.
- Commented-out code — delete it and rely on Git history.
