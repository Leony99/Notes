# Clean Code

Clean Code is a set of principles for writing code that is easy to read, understand, and maintain. The term was popularized by Robert C. Martin ("Uncle Bob") in his book *Clean Code: A Handbook of Agile Software Craftsmanship*.

The core idea is that code is read far more often than it is written. Clean code prioritizes the reader.

## Meaningful Names

Variables, functions, and classes should reveal intent. A good name eliminates the need for a comment.

- Use names that explain **why** something exists, **what** it does, and **how** it is used.
- Avoid single-letter variables (except for loop counters).
- Avoid abbreviations and encodings (`usr`, `d`, `strName`).

*Example:*

```typescript
// bad
const d = new Date();
function calc(a: number, b: number, c: number): boolean {
  return a * b - c > 0;
}

// good
const currentDate = new Date();
function isOrderProfitable(price: number, quantity: number, cost: number): boolean {
  const revenue = price * quantity;
  const profit = revenue - cost;
  return profit > 0;
}
```

## Functions

- A function should do **one thing only** and do it well.
- Keep functions small — ideally under 20 lines.
- Avoid side effects: a function should not change state outside its scope unexpectedly.
- Prefer fewer arguments (0–2 is ideal; 3+ is a warning sign).

*Example:*

```typescript
// bad — does 3 things
function processUser(user: User): void {
  if (!user.email.includes("@")) throw new Error("Invalid email");
  db.save(user);
  mailer.sendWelcome(user.email);
}

// good — each function has one responsibility
function validateEmail(email: string): void {
  if (!email.includes("@")) throw new Error("Invalid email");
}

function saveUser(user: User): void {
  db.save(user);
}

function sendWelcomeEmail(user: User): void {
  mailer.sendWelcome(user.email);
}

function registerUser(user: User): void {
  validateEmail(user.email);
  saveUser(user);
  sendWelcomeEmail(user);
}
```

## No Magic Numbers

Avoid raw numbers or strings scattered throughout the code. Extract them into named constants.

*Example:*

```typescript
// bad
if (user.age >= 18) { allowAccess(); }
setTimeout(callback, 86400000);

// good
const MINIMUM_AGE = 18;
const ONE_DAY_MS = 86_400_000;

if (user.age >= MINIMUM_AGE) { allowAccess(); }
setTimeout(callback, ONE_DAY_MS);
```

## Comments

Good comments explain **why**, not **what**. If the code needs a comment to explain what it does, it should be rewritten.

- Do not use comments to describe obvious code.
- Do not leave TODO comments without a tracking ticket.
- Avoid commented-out code — use version control (Git) instead.

*Example:*

```typescript
// bad
counter++; // increments counter

// good — explains a non-obvious reason
// multiply by 2 because the external lib returns half the actual value (known bug)
const correctedValue = getRawValue() * 2;
```

## DRY – Don't Repeat Yourself

Every piece of knowledge should have a single, unambiguous representation in the system. Duplicated logic means two places to change when requirements evolve.

*Example:*

```typescript
// bad
function createAdminUser(name: string, email: string) {
  const user = { name, email, role: "admin", createdAt: new Date() };
  db.save(user);
  return user;
}
function createGuestUser(name: string, email: string) {
  const user = { name, email, role: "guest", createdAt: new Date() };
  db.save(user);
  return user;
}

// good
function createUser(name: string, email: string, role: string) {
  const user = { name, email, role, createdAt: new Date() };
  db.save(user);
  return user;
}
```

## Formatting

Consistent formatting makes a codebase feel like one person wrote it.

- Use a formatter (Prettier) and a linter (ESLint) — do not format manually.
- Keep related code together; separate unrelated blocks with blank lines.
- Limit line length (80–120 characters is a common convention).
