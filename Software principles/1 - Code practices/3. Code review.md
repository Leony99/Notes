# Code Review

Code review is the practice of having one or more developers examine a colleague's code before it is merged into the main branch. It is one of the most effective practices for catching bugs early, sharing knowledge across the team, and maintaining code quality over time.

## Why It Matters

- Catches bugs and logic errors before they reach production.
- Spreads knowledge — reviewers learn about parts of the codebase they don't own.
- Enforces consistency in style and architecture.
- Encourages better code — knowing someone will read it raises the bar.

## As an Author (submitting code)

- **Keep PRs small.** A pull request with 50–100 lines is easy to review. One with 800 lines will get a shallow review.
- **Write a clear description.** Explain *what* changed, *why*, and *how to test it*. Don't make the reviewer guess.
- **Self-review first.** Read your own diff before requesting a review. You'll catch obvious issues yourself.
- **One concern per PR.** Avoid mixing a bug fix with a refactor with a new feature.

## As a Reviewer

- **Review the logic, not just the style.** Linters handle formatting. Focus on correctness, edge cases, and design.
- **Ask questions, don't just command.** Prefer *"What do you think about extracting this into a separate function?"* over *"Extract this into a function."*
- **Distinguish blocking from non-blocking comments.** Make it clear whether a comment must be resolved before merging or is just a suggestion.
- **Approve explicitly.** Don't leave the author guessing whether silence means approval.
- **Be timely.** A PR that sits unreviewed for 3 days blocks the author and creates merge conflicts.

## What to Look For

**Correctness:**
- Does the logic match the requirements?
- Are edge cases handled (null, empty list, zero, concurrent access)?
- Are errors handled properly?

**Design:**
- Does the change follow the existing architecture?
- Is there duplicated logic that should be extracted?
- Are functions and classes doing one thing?

**Security:**
- Is user input validated and sanitized?
- Are secrets or credentials exposed?

**Tests:**
- Are new behaviors covered by tests?
- Do the tests actually test the right thing?

## Pull Request Template

A good PR template prompts the author to provide the right context:

```markdown
## What changed
<!-- Short description of the change -->

## Why
<!-- Business or technical reason -->

## How to test
<!-- Steps to verify the change manually -->

## Checklist
- [ ] Tests added or updated
- [ ] No console.log left behind
- [ ] Documentation updated if needed
```
